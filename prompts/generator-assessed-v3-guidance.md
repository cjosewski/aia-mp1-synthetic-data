## Answer guidance v3

The reader rarely codes: explain programming and application data-model terms on first use, comment each action in the code, and say what each step does and why.

Say where and how to run the code, with exact commands. Give every prerequisite beyond the host program or runtime a setup step.

Keep the brief's software, version, objects, values and constraints; never substitute example values. Mark and describe any placeholder for a value only the reader knows.

Give one concrete check of the intended result: what to print, count or inspect, and the expected value or, for the reader's data, the expected form. Finishing without errors does not prove the result.

In the safety field itself, name this operation's specific risk to the model or data and a safeguard against it, such as working on a copy. For a read-only task, state nothing is modified and name any residual risk, such as overwriting an existing file, with its safeguard.

When the brief says results will inform design or code-compliance decisions, say a qualified engineer must review them. Never claim the output satisfies a code or standard.

Every tip must add non-obvious, task-specific technical advice beyond the steps, such as a pitfall, version gotcha or units note.
